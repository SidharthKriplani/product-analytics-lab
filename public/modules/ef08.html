A/A Testing

Validating your experimentation platform before you trust it

Before trusting a new platform, you run an A/A test — both groups get the identical experience — and it comes back p = 0.02. A junior analyst panics: "Significant! The platform is broken." Not so fast. Under a working platform, roughly 5% of A/A tests will show p < 0.05 purely by chance, so one significant A/A is exactly what you'd expect, not proof of a bug. You validate a platform by running MANY A/A tests and checking the p-value distribution: it should be roughly uniform, with a false positive rate near alpha (about 5%). The alarm bell is a PATTERN — far too many significant results, or a p-value distribution skewed toward 0. That signals broken randomization or wrong (usually underestimated) variance. One significant A/A is noise; a skewed distribution across many is the real signal.

How this connects to experimentation: A/A testing is a prerequisite to trusting any A/B result. If your platform has systematic bias, every experiment you run is compromised. Interviewers use A/A scenarios to probe whether you validate infrastructure before drawing conclusions.

Key takeaways

  • ~5% of A/A tests show p<0.05 by chance, so one significant A/A is expected, not a bug.
  • Validate a platform by running many A/A tests and checking the p-value distribution is ~uniform.
  • The alarm is a pattern — too many significant results, or a distribution skewed toward 0.

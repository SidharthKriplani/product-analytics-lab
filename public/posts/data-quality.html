Data Quality Checks Before You Start Any Analysis

Nulls, duplicates, grain mismatches, and timestamp anomalies. The checks that catch silent errors before they become wrong conclusions. A checklist with SQL patterns.

Most analysis errors are not statistical — they are data quality errors. A null value treated as zero inflates denominators. A duplicated row from a fan-out join inflates counts. A timestamp stored in UTC interpreted as local time shifts your daily buckets by 5 to 8 hours. These errors produce numbers that look plausible and are completely wrong. The five dimensions of data quality — completeness, consistency, accuracy, timeliness, and uniqueness — each require a specific check before you touch any metric.

The Five Checks You Run Before Anything Else

Completeness: check the null rate for every column you plan to use. SELECT COUNT(*) as total, COUNT(column_name) as non_null, ROUND(100.0 * COUNT(column_name) / COUNT(*), 1) as fill_rate FROM table tells you what fraction of rows have usable values. A 15% null rate on seller_id in the orders table means 15% of orders are unattributable — that changes your seller-level analysis fundamentally. Consistency: check whether the same entity (a user, a seller, an order) has consistent values across tables. A user in the users table with status = "active" who has no events in the events table for 90 days is an inconsistency that may signal a data pipeline problem. Uniqueness: check for duplicate rows at the grain you expect. SELECT COUNT(*), COUNT(DISTINCT primary_key) FROM table — if these numbers differ, you have duplicates at the supposed primary key level.

Crafted orders table audit before A/B test analysis: -- Step 1: Row count and date range
SELECT COUNT(*) as rows, MIN(created_at), MAX(created_at) FROM orders;
-- Result: 184,200 rows, 2024-01-01 to 2024-03-31 ✓

-- Step 2: Null rates on key columns
SELECT
ROUND(100.0 * COUNT(buyer_id) / COUNT(*), 1) AS buyer_fill_rate,
ROUND(100.0 * COUNT(seller_id) / COUNT(*), 1) AS seller_fill_rate,
ROUND(100.0 * COUNT(order_value) / COUNT(*), 1) AS value_fill_rate,
ROUND(100.0 * COUNT(experiment_variant) / COUNT(*), 1) AS variant_fill_rate
FROM orders;
-- Result: buyer 98.3%, seller 99.1%, value 97.7%, variant 71.4% ← problem
-- 28.6% of orders have no experiment_variant — these are pre-experiment or untracked orders

-- Step 3: Uniqueness check
SELECT COUNT(*) as total, COUNT(DISTINCT order_id) as unique_orders FROM orders;
-- If total > unique_orders: duplicates exist — investigate before computing any metrics

-- Step 4: Distribution check for value column
SELECT
PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY order_value) AS median,
PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY order_value) AS p95,
MAX(order_value) AS max_value
FROM orders WHERE order_value IS NOT NULL;
-- A max_value of $15,000 when median is $62 suggests outliers that may need capping

The Fan-Out Join Problem

The most silent data quality error in SQL is a fan-out join: joining a table to another table where the join produces more rows than expected because the join key is not unique on one side. Joining the orders table to the reviews table on order_id, where one order can have multiple reviews, produces one row per review — not one row per order. Every user-level metric you compute from this joined table is inflated by the number of reviews per order. The check: after any join, verify that COUNT(*) in the result equals the expected number of rows at the intended grain. If it doesn't, you have a fan-out and need to aggregate before joining.

The pre-analysis checklist: 1. Row count and date range — does the data cover the expected period? 2. Null rates on all key columns — are the columns you plan to use sufficiently populated? 3. Uniqueness at the expected grain — any duplicates at the primary key level? 4. Distribution of numeric columns — any outliers that could distort means? 5. After joins: verify row count at expected grain — did the join fan out? 6. Timestamp timezone — are dates in UTC, local, or mixed? How do daily buckets behave at midnight?
